# Apex AI Arabia — Backend & Integration Engineer Assessment

## Engineering Requirements Specification

**Document status:** Revised draft for final architecture review
**Source:** Apex AI Arabia Backend & Integration Engineer 48-Hour Assessment
**Purpose:** Translate the assessment into concrete, traceable engineering requirements and explicit prototype decisions.

---

# 1. Purpose

The system is an integration backend for a Saudi private healthcare group operating six hospitals and a centralized contact center.

The prototype will demonstrate a referral and appointment workflow in which the backend:

1. receives a referral request;
2. authenticates and authorizes the caller;
3. validates the request;
4. prevents duplicate processing;
5. checks eligibility through a mock EHR;
6. sends appropriate referral information to the provided AI service;
7. applies routing rules;
8. creates or updates a CRM case;
9. publishes processing/status events;
10. maintains an auditable processing history;
11. handles transient failures through bounded retries;
12. moves unsuccessfully processed work to a dead-letter mechanism;
13. provides sufficient operational evidence for production handover and future scaling.

The prototype must use **synthetic/mock data only**.

# 3. Functional Requirements

## FR-01 — Referral Intake

### Source

Assessment referral workflow and required backend service.

### Engineering requirement

The API shall expose a versioned endpoint for submitting a referral:

```http
POST /api/v1/referrals
```

The endpoint shall:

* accept a structured referral payload;
* authenticate the caller;
* authorize the requested operation;
* validate the request;
* require an idempotency key;
* create a referral record;
* create the corresponding processing event;
* initiate asynchronous processing;
* return a referral identifier and processing status.

### Initial response

```http
202 Accepted
```

```json
{
  "referral_id": "ref_001",
  "status": "PROCESSING"
}
```

The API shall not wait for the complete EHR → AI → routing → CRM workflow before responding.

### Transactional creation

Referral persistence and creation of the corresponding processing event shall occur within the same database transaction.

The prototype shall use a **transactional outbox pattern**:

```text
Database transaction
 ├── referral record
 └── outbox event
          ↓
      committed
          ↓
    Outbox publisher
          ↓
        Queue
```

This prevents the referral from being successfully persisted while its processing event is silently lost because queue publication failed.

# FR-02 — Request Validation

The API shall validate incoming referral requests before creating processing work.

Validation shall include:

* required fields;
* supported field formats;
* valid specialty values where applicable;
* valid hospital identifiers where applicable;
* request structure;
* idempotency key presence and format.

Invalid requests shall receive a structured `4xx` response and shall not create referral processing work.

---

# FR-03 — Authentication

The API shall authenticate callers using bearer-token authentication representative of an enterprise identity provider.

For the prototype:

* tokens may be generated by a mock identity provider;
* no real customer credentials shall be used;
* authentication logic shall be isolated behind a replaceable identity/security boundary.

Unauthenticated requests shall be rejected.

Authentication failures shall not expose implementation details or sensitive information.

---

# FR-04 — Authorization

Authentication alone shall not grant unrestricted access.

The prototype shall demonstrate role-based authorization with a minimal role model.

Example roles:

```text
contact_center_agent
integration_service
operations_admin
```

### Authorization responsibilities

#### `contact_center_agent`

May:

* submit referrals;
* retrieve referrals within the agent's authorized hospital scope.

An agent shall not be able to retrieve another hospital's referral merely by knowing or guessing its referral ID.

#### `integration_service`

May perform service-to-service operations required by the referral workflow.

#### `operations_admin`

May:

* inspect operational referral state;
* inspect failed processing;
* perform authorized DLQ recovery/reprocessing operations.

### Hospital scope

The prototype shall represent hospital scope as an authorization attribute.

For example:

```text
agent_id = agent_001
role = contact_center_agent
hospital_scope = RIYADH-01
```

The exact production authorization model is outside prototype scope.

Authorization decisions shall follow least-privilege principles.

# FR-05 — Idempotent Referral Processing

## Objective

The same logical referral submission must not result in duplicate downstream processing.

## Idempotency mechanism

Clients shall provide:

```http
Idempotency-Key: <unique-operation-key>
```

Idempotency shall be scoped to the authenticated client/service identity.

The effective uniqueness boundary shall therefore be:

```text
(client_id, idempotency_key)
```

rather than a globally unique key string.

The backend shall persist:

* client/service identity;
* idempotency key;
* request hash;
* associated referral ID;
* processing status;
* timestamps;
* sufficient result information to safely handle retries.

## Required behavior

### New key

Create the idempotency record and referral processing state.

### Same client + same key + same request

Return the existing referral/result.

The workflow must **not execute again**.

### Same client + same key + different request

Return:

```http
409 Conflict
```

Example:

```json
{
  "error": {
    "code": "IDEMPOTENCY_KEY_REUSED",
    "message": "The idempotency key was previously used with a different request.",
    "request_id": "req_123"
  }
}
```

No sensitive patient information shall be exposed.

### Same key while processing

Return the existing referral and its current status.

Example:

```json
{
  "referral_id": "ref_001",
  "status": "PROCESSING"
}
```

A second processing workflow shall not be started.

## Concurrency

The database shall enforce uniqueness on:

```text
(client_id, idempotency_key)
```

Application-level existence checks alone are insufficient because concurrent requests could otherwise pass the check simultaneously.

The implementation shall include a test demonstrating protection against concurrent duplicate submissions.

## Retention

For the prototype, idempotency records shall be retained for **24 hours**.

This is a provisional operational decision for the assessment and would be configurable in a production implementation based on expected client retry behavior and business requirements.

The backend shall communicate with a mock EHR through a dedicated adapter/interface.

The EHR integration shall support a credible request/response contract.

The adapter shall isolate the referral workflow from the concrete EHR implementation.

Example conceptual operation:

```text
check_patient_eligibility()
```

The mock EHR shall be capable of producing:

* successful eligibility responses;
* ineligible responses;
* transient technical failures;
* non-retryable failures.

# FR-07 — Eligibility

The system shall perform an eligibility check before continuing the referral workflow.

For the prototype, eligibility rules will be simplified mock rules because the assessment does not provide the healthcare group's actual eligibility policy.

A successful EHR response containing:

```json
{
  "eligible": false
}
```

shall be treated as a **business outcome**, not as a technical integration failure.

The referral shall transition to:

```text
ELIGIBILITY_FAILED
```

and the normal referral workflow shall **stop**.

The system shall not send an ineligible referral to the AI service, routing logic, or CRM unless an explicitly documented future/manual override mechanism exists.

No manual eligibility override is included in the prototype.

### Technical failure

By contrast:

```text
EHR timeout
EHR connection failure
EHR 5xx
```

shall be treated as technical failures and handled according to the retry policy.

### Terminal state

`ELIGIBILITY_FAILED` is a terminal business outcome for the prototype.

The contact center can retrieve the status through the referral status endpoint.

A manual appeal/override workflow is outside prototype scope.

# FR-08 — AI Integration

The AI model is supplied by another Apex team.

The prototype shall therefore implement the **integration boundary**, not an AI model.

The backend shall communicate with the AI service through a dedicated adapter.

For the prototype, the AI service contract will be defined explicitly and treated as a mock representation of the upstream Apex AI service.

Example conceptual response:

```json
{
  "classification": "CARDIOLOGY",
  "urgency": "HIGH",
  "confidence": 0.94
}
```

These fields are prototype contract decisions and are **not claimed to originate from the assessment**.

## AI output authority

AI output shall be treated as **advisory input to the routing decision**, not as an unrestricted authoritative decision.

The deterministic routing component remains responsible for the final hospital-routing decision.

For example:

```text
AI classification
       +
Referral attributes
       +
Hospital/routing rules
       ↓
Deterministic routing decision
```

The prototype shall document how conflicting AI output and referral attributes are handled.

The exact production AI model, model governance, model accuracy requirements, and production model contract are outside prototype scope.

## AI failure handling

Potential retryable failures:

* timeout;
* connection failure;
* `429`;
* `5xx`.

Potential non-retryable failures:

* invalid request;
* unauthorized request;
* forbidden request;
* unsupported resource;
* non-transient processing rejection.

The AI adapter shall prevent upstream-specific implementation details from leaking into the referral service.

# FR-09 — Routing

The backend shall determine the appropriate hospital/routing destination using explicit routing rules.

For the prototype:

* routing rules shall be deterministic;
* rules may use referral specialty;
* rules may use AI classification/urgency as advisory input;
* rules may use hospital preference;
* rules may use mock hospital availability;
* rules shall be documented;
* rules shall be isolated from the API layer;
* production routing policy shall be treated as customer-specific configuration.

The prototype shall not claim to reproduce the healthcare group's actual routing policy.

The routing component shall produce a structured result such as:

```json
{
  "hospital_id": "RIYADH-01",
  "reason": "CARDIOLOGY_HIGH_URGENCY"
}
```

# FR-10 — CRM Integration

The backend shall integrate with a mock CRM case API through a dedicated CRM adapter.

The adapter shall support:

* case creation;
* case lookup;
* case update;
* simulated transient failures;
* simulated duplicate-case behavior.

## External reference

`external_reference` is a **client-supplied business reference** and is distinct from the system-generated internal `referral_id`.

Example:

```text
external_reference = REF-10001
referral_id = ref_001
```

The external reference may be used for correlation with upstream systems and for safe downstream duplicate resolution.

## Duplicate CRM case

A CRM duplicate-case response shall not automatically be treated as a transient failure.

Where possible, the integration shall resolve the existing case using the stable external reference.

Example:

```text
external_reference = REF-10001
        ↓
CRM lookup
        ↓
CASE-8472 already exists
        ↓
associate existing case
        ↓
continue safely
```

The implementation shall avoid blindly creating duplicate downstream cases.

# FR-11 — Event Publishing

The system shall publish referral processing events through an event/queue abstraction.

Events shall decouple API intake from downstream referral processing.

## Transactional outbox

The referral record and initial processing event shall be persisted in the same database transaction.

Example:

```text
BEGIN TRANSACTION

INSERT referral
INSERT outbox_event

COMMIT
```

An independent outbox publisher shall:

1. find unpublished outbox events;
2. publish them to the queue;
3. mark them as published;
4. retry publication when the queue is temporarily unavailable.

This addresses the failure case where the referral database write succeeds but queue publication fails.

## Outbox recovery

An unpublished outbox event shall remain recoverable from the database.

A publisher failure must therefore not permanently lose the processing event.

The prototype shall demonstrate or test this behavior.

## Event contents

Events shall contain sufficient metadata for processing and troubleshooting without unnecessarily carrying sensitive patient information.

Example:

```json
{
  "event_id": "evt_001",
  "event_type": "REFERRAL_PROCESSING_REQUESTED",
  "referral_id": "ref_001",
  "attempt": 1,
  "created_at": "2026-09-24T12:00:00Z"
}
```

The queue implementation may be mocked for the assessment, but its interface must represent a credible production integration boundary.

# FR-12 — Referral Status Retrieval

The API shall expose:

```http
GET /api/v1/referrals/{referral_id}
```

The endpoint shall return the current referral state from the system of record.

Example:

```json
{
  "referral_id": "ref_001",
  "status": "COMPLETED",
  "crm_case_id": "CASE-8472"

```

The database shall be the authoritative source for the referral's application-level processing state.

The endpoint shall enforce the authorization rules defined in FR-04.

At minimum:

* contact-center agents can only access referrals within their authorized hospital scope;
* operations administrators can access referrals required for operational support.

The system shall not rely on the obscurity of `referral_id` as an authorization mechanism.

# FR-13 — Retry Handling

The system shall retry **transient technical failures** from external integrations.

## Retryable failures

At minimum:

* connection timeout;
* connection failure;
* HTTP `429`;
* HTTP `500`;
* HTTP `502`;
* HTTP `503`;
* HTTP `504`.

## Non-retryable failures

At minimum:

* HTTP `400`;
* HTTP `401`;
* HTTP `403`;
* HTTP `404`;
* malformed requests;
* business-rule rejection;
* eligibility rejection.

## Prototype retry policy

Maximum attempts:

```text
3
```

Backoff:

```text
Attempt 1
   ↓
500 ms
   ↓
Attempt 2
   ↓
1 second
   ↓
Attempt 3
   ↓
failure → DLQ
```

This is a prototype policy selected to demonstrate bounded retry behavior. It is not claimed to be the customer's production retry policy.

## Retry granularity

Retries shall occur at the **failed integration step**, rather than restarting the entire referral workflow unnecessarily.

Example:

```text
EHR       COMPLETED
AI        COMPLETED
Routing   COMPLETED
CRM       FAILED
```

A CRM retry should resume from the CRM step.

It should not automatically call EHR and AI again.

This requires the workflow to persist sufficient progress/state to identify the failed processing stage.

## Retry safety

Each integration adapter shall be designed so that retries do not blindly create duplicate downstream records.

Idempotency and/or lookup mechanisms shall be used where downstream operations have side effects.

Retry behavior shall be centralized rather than independently reinvented by every integration.

---

# FR-14 — Dead-Letter Handling

When a retryable operation fails after the maximum configured attempts, the event shall be moved to a dead-letter mechanism.

A DLQ record shall contain enough information to support diagnosis and recovery.

Example:

```json
{
  "event_id": "evt_001",
  "referral_id": "ref_001",
  "failed_step": "CRM",
  "failure_code": "CRM_UNAVAILABLE",
  "attempts": 3,
  "failed_at": "2026-09-24T12:05:00Z"
}
```

Sensitive patient information shall not be unnecessarily copied into the DLQ payload.

The referral status shall reflect that processing requires operational attention.

Example:

```text
DEAD_LETTER
```

## DLQ authorization

Only the `operations_admin` role shall be permitted to trigger DLQ replay/reprocessing.

DLQ replay shall be audited.

The replay mechanism shall use the existing idempotency and downstream duplicate-protection mechanisms to prevent unsafe duplicate processing.

## Runbook

The runbook shall explain:

* how operators identify a DLQ item;
* how the underlying failure is investigated;
* how a DLQ item is authorized for replay;
* how replay is performed;
* what safeguards prevent duplicate downstream processing.

---

# FR-15 — Auditability

The system shall maintain an audit trail of significant referral-processing and security-relevant actions.

Audit records shall capture, where appropriate:

* timestamp;
* actor/service identity;
* action;
* resource/reference ID;
* outcome;
* correlation/request ID.

## Auditable actions

At minimum, the prototype shall audit:

* referral creation;
* significant referral state transitions;
* external integration outcomes;
* CRM case creation/update;
* retry exhaustion;
* DLQ creation;
* DLQ replay;
* authorization failures;
* authentication failures where appropriate.

Example:

```json
{
  "action": "CRM_CASE_CREATED",
  "resource_id": "ref_001",
  "actor": "referral_worker",
  "outcome": "SUCCESS",
  "request_id": "req_123",
  "timestamp": "2026-09-24T12:03:00Z"
}
```

Audit records shall avoid unnecessary patient-sensitive information.

Audit records are for accountability and traceability and shall not become a copy of the clinical payload.

---

# FR-16 — Structured Errors

All public API errors shall follow a consistent structure.

Example:

```json
{
  "error": {
    "code": "CRM_UNAVAILABLE",
    "message": "The CRM service is temporarily unavailable.",
    "request_id": "req_123",
    "retryable": true
  }
}
```

Errors shall:

* provide actionable machine-readable codes;
* provide a request/correlation identifier;
* distinguish retryable from non-retryable conditions where appropriate;
* avoid stack traces;
* avoid unnecessary sensitive information.

# NFR-11 — API Rate Limiting

Public API operations shall be protected against accidental or abusive request
bursts. Limits shall be shared across horizontally scaled API instances and
scoped by authenticated client identity and operation. Failed authentication
attempts shall be limited by network peer identity.

The implementation shall:

* return HTTP `429` with the standard error envelope and `Retry-After`;
* avoid storing JWTs, patient identifiers, or clinical payloads in limiter keys;
* exclude health probes;
* expose policy values through environment configuration;
* document behavior when the limiter backend is unavailable;
* retain an independent gateway/WAF limit in the target production architecture.

| Sensitive data        | Synthetic only                                |
| API status            | Database is application-level source of truth |
| Authorization         | Role + hospital scope                         |
| Logging               | Structured, minimized                         |
| Audit                 | Business + security-relevant events           |

These are **prototype engineering decisions**, not claims about the customer's production environment.

# 12. Traceability Principle

Every significant implementation decision should be traceable through:

```text
Assessment requirement
        ↓
Engineering interpretation
        ↓
Architecture decision
        ↓
Implementation
        ↓
Test/evidence
```

The prototype should not claim that an implementation detail was explicitly required by the assessment when it is actually an engineering assumption or design choice.

The purpose of this document is therefore not to reproduce the assessment, but to establish a defensible engineering interpretation of it.
